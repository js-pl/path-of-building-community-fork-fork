# Path of Building Community Fork Fork

Unofficial rewrite of Path of Building Community (PoE 1): Rust engine compiled to
WebAssembly plus a TypeScript web frontend.
See `docs/design.md` before making architectural decisions.

## Project overview
- `crates/` holds the Rust workspace:
  - `engine`: the typed engine (data model, mod parser, calcs, power, items,
    tree), shipped in the browser
  - `session`: the engine API (build sessions answering JSON commands) and
    the native and oracle `Session`s the tests compare it with
  - `wasm` (C ABI for the browser), `cli` (`pob`: serve, bundle, bench,
    history, settings)
  - `history` (a build's versions, one git repository per build, written
    with the installed git; optional), see `docs/history.md`
  - `settings` (the app's `settings.json`, e.g. the history's git), see
    `docs/settings.md`
  - `importer` (reads upstream's data and ModParser tables at build time),
    `gamedata` (the engine's typed game data from the importer's tables, in
    `engine::codec`'s binary form)
  - `lua` (the Lua library pieces the engine ships: values, LuaJIT's table
    order, patterns, number formatting), `luai` (the interpreter the
    importer runs upstream's data files with)
  - `equivalence` (tests against the oracle), `testkit` (sharded test runs)
  - until sub-step 8 of [the deletion](docs/drop-translation.md#step-4-in-sub-steps):
    `upstream` (upstream's whole program translated to Rust by luagen in its
    build script; never edit generated code, fix luagen or the runtime),
    which the session's `translation` feature and the bench still use
- `upstream/PathOfBuilding` is upstream PoB Community as a submodule, pinned to a commit on upstream `dev`; never edit it
- `docs/` holds design decisions; `docs/drop-translation.md` tracks removing
  the translation
- `oracle/` runs upstream headless on LuaJIT as the test reference:
  `tests/oracle` is its committed output, and `oracle/session.lua` answers
  the engine API live for the session and variant tests (CI runs the
  session test on it, `SESSION_REFERENCE=oracle`; locally it defaults to
  the translation until sub-step 8), see `oracle/README.md`
- `sync/manifest.toml` maps every upstream file to its port; update it when
  porting, `sync/check.py` checks it
- `crates/engine/src/mod_parser/generated.rs` is generated by
  `cargo run -p importer --bin portgen`; never edit it

## Coding guidelines
- code and comments are written in english
- the typed engine is free-form, not mirrored on upstream's files; record in
  `sync/manifest.toml` where each upstream file is ported and the upstream
  commit it is in sync with
- sync with upstream through the `sync` skill
- never commit GGG game data or art; read data from the submodule at build time
- expected test values come from the upstream oracle only; never edit oracle
  outputs, the corpus or `tests/tolerances.toml` to make a test pass

## Git workflows
- trunk based development
- each feature gets its own feature branch
- never push directly to main, work via PRs
- always squash merge PRs, and only with green CI
- merge continually: once a step works (its tests and CI's checks pass),
  open a PR for it right away and squash merge it yourself if you are
  happy with the change; no owner approval is needed. Don't let finished
  work pile up on an unmerged branch
- keep PRs small, one working step each; start the next step from the
  latest `main` once the previous PR is merged
- before ending a session, open a PR for any finished, pushed work that
  has none and merge it once CI is green; say in the handoff which PRs
  are still open and why
- be brief in commit messages
